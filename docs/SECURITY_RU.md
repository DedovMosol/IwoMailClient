## Если утрачен хеш пароля блокировки

Когда сессия заблокирована, блокировка включена, а проверочного хеша на устройстве нет, `MainActivity` показывает экран восстановления. Это **не сброс забытого пароля**, если его хеш сохранился. Нужен пароль активного почтового аккаунта (первого, если активный не выбран). `AccountRepository.verifyAccountPassword` сверяет его локально с сохранённым паролем. Если сохранённого пароля нет, для Exchange выполняется запрос доступа к ящику на используемом адресе аккаунта. Одного ответа OPTIONS недостаточно. Для аккаунтов с клиентским сертификатом и для IMAP/POP3 сетевую проверку пароля этот экран не выполняет. Если проверить пароль невозможно, доступ не открывается. Успешная проверка отключает блокировку и биометрический вход; новый пароль приложения задаётся в настройках. Если аккаунтов нет, блокировка снимается без пароля ящика.

Блокировка защищает интерфейс, но не шифрует базу Room и не останавливает фоновую синхронизацию. При включённой блокировке виджет и уведомления скрывают содержимое даже при утрате хеша. На Android 13+ отключаются снимки для «Недавних», на Android 8–12 при включённой функции действует `FLAG_SECURE`.

## Модель угроз

Клиент Exchange для **Exchange 2007 SP1 … 2013**: Exchange ActiveSync
(EAS, WBXML) и Exchange Web Services (EWS, SOAP).

## Хранение учётных данных

Учётные данные хранятся на устройстве и используются для входа по TLS на настроенный сервер Exchange, IMAP или POP3. Для Exchange у аккаунта также может быть указан резервный адрес.

- **Основной путь:** `EncryptedSharedPreferences` (AES-256-SIV для ключей,
  AES-256-GCM для значений), мастер-ключ в **Android Keystore**, при наличии
  на железе (`EncryptedStoreProvider`).
- **Запасной путь:** если Keystore или `EncryptedSharedPreferences` не
  встают (часть прошивок, перенос устройства), используется
  `ObfuscatedSharedPreferences` — XOR с ключом PBKDF2-HMAC-SHA256 от
  `ANDROID_ID`. Это **обфускация, не шифрование**. Журнал пишет
  `SecurityTelemetry`. Текущий бэкенд — `PasswordStorage.isUsingInsecureStorage()`
  и `AppLockManager.isUsingInsecureStorage()`, не флаг журнала.
- **Fail-closed:** при деградации в «Безопасности» появляется переключатель
  (по умолчанию выкл.). Если включить, новый пароль ящика и пароль блокировки
  приложения в обфусцированное хранилище не пишутся. Уже сохранённое остаётся.
  Если новый ящик не смог записать пароль, строка аккаунта откатывается, без
  секрета в БД не остаётся. Текст Toast берётся из `AppLanguageCode`
  (загрузка в `Application` до `AppLockManager.init`).
- **Блокировка приложения** (по желанию): PBKDF2-HMAC-SHA256, 600 000 итераций
  (OWASP), соль, хранится только хеш. Холодный старт — заблокировано. Тот же
  `EncryptedStoreProvider`, что у паролей ящиков.

## Транспорт

- **Без cleartext.** `network_security_config.xml`:
  `cleartextTrafficPermitted="false"`, обычный HTTP отклоняется.
- **Корни доверия.** Канал обновлений (`update.json`, APK) доверяет **только
  системным УЦ**. Exchange — системным и, запасным путём, **пользовательским
  УЦ**: корпоративные сертификаты часто выпускает внутренний УЦ, установленный
  как user CA. Следствие: user CA на устройстве (пользователь, MDM, вредонос,
  которому пользователь разрешил установку) может перехватывать трафик Exchange.
  Pinning сертификата это снимает для данного ящика.
- **Версии TLS.** 1.3/1.2, если сервер умеет. 1.1/1.0 остаются (Conscrypt,
  клиенты Exchange отдают TLS 1.0–1.3 одним рукопожатием OkHttp
  `COMPATIBLE_TLS`, без отдельного `MODERN_TLS`), иначе Exchange 2007 SP1
  недоступен. Канал обновлений — `MODERN_TLS` (TLS 1.2+).
- **Явное доверие ключу:** после подтверждения отпечатка закрепляется SHA-256 открытого ключа сервера (SPKI). В этом режиме важен тот же ключ, а не имя или срок сертификата. Поэтому первый отпечаток нужно сверить с администратором по независимому каналу. Для резервного адреса есть отдельное закрепление. Импорт сертификата сервера с проверкой имени и клиентский сертификат для mTLS — другие механизмы.
- **IMAP/POP3:** JavaMail использует TLS сразу либо требует STARTTLS/STLS перед входом. Снятый флажок прямого TLS не разрешает передачу пароля открытым текстом.
- **`acceptAllCerts` только явно и по умолчанию выкл.** Отдельный HTTP-клиент,
  другие ящики не ослабляются.
- **Аутентификация.** EAS: Basic по TLS. EWS: сначала Basic, затем NTLMv2.
  При редиректе на другой хост OkHttp снимает `Authorization`, учётные данные
  уходят только на адреса из аккаунта (основной и, если задан, резервный).

## Локальные данные

- Почта, контакты, календарь, задачи и заметки — Room в приватном хранилище
  приложения, вложения, исходящие и импортированные клиентские сертификаты —
  в приватных файлах.
- **Без бэкапа и без переноса устройства.** `android:allowBackup="false"`
  отключает бэкап на Android 11 и ниже и облачный бэкап на 12+, но не D2D
  на 12+. Поэтому `data_extraction_rules.xml` исключает всё приватное хранилище
  и из облака, и из переноса.

## Root и скомпрометированные устройства

- **Приложение не ищет root и не отказывает таким устройствам.** Это сознательно:
  FOSS-клиент не должен отказывать хозяину устройства, а детекция root легко
  обходится.
- **Не падает:** нет Keystore (часто на кастомных прошивках) — запасная
  обфускация, не отказ.
- **Ограничение платформы:** с root любой процесс может читать чужое приватное
  хранилище и, в зависимости от прошивки, ослабить Keystore. Полностью закрыть
  извлечение секретов при злонамеренном root нельзя. На недоверенном root
  устройстве считайте учётные данные потенциально раскрытыми.

## Недоверенный ввод

- Просмотр HTML-письма очищает разметку, запрещает отправку форм и смену базового URL через CSP. Только нажатие на ссылку в основной странице может открыть браузер (`http`/`https`), номеронабиратель (`tel`) или редактор письма (`mailto`). Автоматические переходы и переходы из фреймов игнорируются.
- В `EasXmlParser.createParser` и `CalendarCategoryService.parseCategoryListXml` отключается обработка DOCTYPE. Не весь EWS/SOAP использует эти парсеры: см. [состояние миграции](XMLPULLPARSER_MIGRATION_PLAN.md).
- Пути синка, которые могут удалять локальные данные (задачи, заметки, контакты,
  календарь), удаляют только по полному снимку сервера. Обрезанный, ошибочный
  или частичный ответ считается неполным, обрыв связи не вытирает локальные
  данные.

## Вне объёма

- Защита от root-устройства под контролем атакующего (см. выше).
- Безопасность сервера и политики ящика Exchange.
- Сетевой противник, который контролирует УЦ, которому доверяет устройство
  (системный или пользовательский), если у ящика нет pinning.
